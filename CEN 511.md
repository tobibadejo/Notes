**b)** Distinguish between general-purpose computing systems and embedded systems in terms of design goals, resource usage, and typical deployment environments. **(3 marks)**

1. Design Goals
**General-Purpose Computing Systems**: Engineered to handle **multiple, varied tasks** and run a wide array of user applications rather than being tied to a single operation[1]. Their core design goal is broad computational flexibility and versatility.

**Embedded Systems**: Designed specifically for a **dedicated purpose** to maximize task functionality, efficiency, and operational reliability[1]. Because the system is built to perform a single distinct task, unnecessary hardware and software features are intentionally omitted.

2. Resource Usage & Hardware Architecture.
**General-Purpose Computing Systems**: Rely primarily on **microprocessors**, which are costlier and require external peripheral chips and modules to handle memory and hardware interfacing. Hardware resources are scaled for high computational capacity rather than minimizing physical space or power.

**Embedded Systems**: Prioritize **small physical size, low cost, and high resource efficiency. They frequently utilize **microcontrollers**—computers-on-a-chip that integrate processor cores, program ROM, RAM, and direct input/output (I/O) capabilities onto a single chip to interface directly with hardware without extra resource overhead.

3. Typical Deployment Environments
**General-Purpose Computing Systems**: Deployed as standalone computing setups or in multi-user environments where direct computation itself is the system's primary function

**Embedded Systems**: Placed **inside larger host systems** where the principal function of the overall system is non-computational (e.g., an automated machine or vehicle), acting as a specialized internal control subsystem.

You are developing an embedded system for a smart irrigation controller that must respond promptly to soil moisture changes, pump failure alerts, and low-power conditions.
**a)** Define interrupt handling in embedded microcontrollers by explaining how a typical microcontroller detects, prioritizes, and services interrupts. **(5 marks)**

ANS: In an embedded microcontroller, **interrupt handling** is an event-driven mechanism that allows internal peripheral events or external hardware signals to temporarily suspend the main program loop. Instead of forcing the CPU to continuously waste clock cycles checking sensors in a loop (polling), interrupts enable rapid, on-demand task switching. This allows the microcontroller to rest in a low-power **Sleep mode** to extend battery life, waking up only when an event requires immediate processing.

**1. Detection (Signal Sensing & Flag Registration)**
**Hardware Signal Trigger:** An external pin detects a voltage transition (such as an edge or level trigger from a pump fault or moisture sensor), or an internal peripheral triggers an event (such as a timer overflow).
**Flag Setting & Masking:** The hardware sets a specific **Interrupt Flag bit** in a Special Function Register (SFR). If both the individual **Interrupt Enable (IE)** bit for that source and the **Global Interrupt Enable (GIE)** bit are set, the CPU completes its current instruction cycle and initiates the interrupt sequence.

**2. Prioritization (Resolving Concurrent Requests)**
**Priority Evaluation:** When multiple interrupt requests occur simultaneously (for example, a critical pump failure alert occurring at the same time as a routine soil moisture timer), the internal **Interrupt Controller** evaluates their hardware-assigned or software-configured priority levels.
**Preemption:** Critical safety conditions (such as low-power warnings or hardware pump failures) are granted higher priority, allowing them to immediately preempt (pause) lower-priority task handlers.

**3. Servicing (Executing the Interrupt Service Routine - ISR)**
**Context Saving:** The CPU saves its current execution state by pushing the **Program Counter (PC)**, status registers, and key CPU flags onto the RAM stack.
**Vector Lookup & ISR Jump:** The CPU fetches the memory address corresponding to the event from the **Interrupt Vector Table** and jumps to execute that specific **Interrupt Service Routine (ISR)**.
**Flag Clearing & Return:** Within the ISR, the software clears the interrupt flag bit to prevent repeated re-triggering. Executing a Return-from-Interrupt instruction (such as `RETI`) pops the saved execution state off the stack, restoring the Program Counter so the CPU seamlessly resumes the main program right where it left off.

// --- Pin Assignments ---
const int VEH_GREEN  = 8;   // Vehicle Green LED
const int VEH_YELLOW = 9;   // Vehicle Yellow LED
const int VEH_RED    = 10;  // Vehicle Red LED
const int PED_GREEN  = 11;  // Pedestrian Green LED

void setup() {
  // Configure traffic light control pins as digital outputs
  pinMode(VEH_GREEN, OUTPUT);
  pinMode(VEH_YELLOW, OUTPUT);
  pinMode(VEH_RED, OUTPUT);
  pinMode(PED_GREEN, OUTPUT);
}

void loop() {
  // 1. Vehicle Green ON for 45s (Pedestrian Green OFF)
  digitalWrite(VEH_GREEN, HIGH);
  digitalWrite(VEH_YELLOW, LOW);
  digitalWrite(VEH_RED, LOW);
  digitalWrite(PED_GREEN, LOW);
  delay(45000); // 45 seconds

  // 2. Vehicle Yellow ON for 5s (Pedestrian Green OFF)
  digitalWrite(VEH_GREEN, LOW);
  digitalWrite(VEH_YELLOW, HIGH);
  digitalWrite(VEH_RED, LOW);
  digitalWrite(PED_GREEN, LOW);
  delay(5000);  // 5 seconds

  // 3. Vehicle Red ON & Pedestrian Green ON for 20s
  digitalWrite(VEH_GREEN, LOW);
  digitalWrite(VEH_YELLOW, LOW);
  digitalWrite(VEH_RED, HIGH);
  digitalWrite(PED_GREEN, HIGH);
  delay(20000); // 20 seconds
}
